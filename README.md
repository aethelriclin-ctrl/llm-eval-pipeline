# 大模型评测流水线（LLM Eval Pipeline）

一个从零搭起来的大模型评测脚本：**自定义测试集 → 多类型评分器 → 分类准确率 → 失败案例归因**。

重点不在于"我测了一个模型"，而在于——
**我能说清楚每一次失败到底该怪谁**：是模型不会，还是我的题目/尺子有问题。

---

## 一句话结论

> 对 `deepseek-flash` 跑 11 道题：**准确率 11/11（100%），总成本 0.014324 元，平均每题 0.001302 元。**
> 但**满分不是好消息**——失败归因表随之变空，评测失去了信号。
> 本项目最有价值的产出全部来自失败样本：**失败案例库 6 条记录里，5 条是失败记录，
> 而这 5 条经人工复核后全部属评测侧**（2 次评分器误判、2 次题目缺陷、1 次题目条件缺失）；
> 第 6 条记的不是失败，而是"**零失败导致评测失去信号**"这件事本身。
>
> **成本在多次跑测间波动约 1.9 ~ 2.6 倍**：思考模式下输出 token 不稳定。
> 精确到单次的成本数字不足以作为结论，**成本评估需要多次运行取区间**。
> 可核的基准值：`results.json` 的 **0.014324 元**；
> 单题成本波动按题库分别统计——**基础库 5 轮 flash 2.64 倍 / pro 2.09 倍；难题库 3 轮 flash 1.87 倍 / pro 2.00 倍**。

> 一次换模型的对照（旧模型 `deepseek-chat` 已停服）：**算术推理 1/3 → 3/3，事实问答 2/2 → 1/2**，
> 说明同一套题在不同模型上暴露的短板完全不同——**总分会掩盖这种差异，必须分类看。**

> 🔍 **多模型对照的结论（见下）**：
> `flash` 与 `v4-pro` 在 17 道题上**精度零差异**（含两道只差两三个字、答案相反的量词陷阱题）；
> `flash` 处理一道题**平均约 0.001 元**（基础库）/ **约 0.003 元**（难题库）（均为多轮均值），
> 但**跑测之间会跳约 1.9~2.6 倍**，**不能按上次花费预估**；
> **延迟上两者基本持平**：基础库 5 轮均值 1.245s vs 1.261s（差 1.3%）、
> 难题库 3 轮均值 1.892s vs 1.790s（差 5.7%），**两个题库的差距都小于跑测之间的轮间波动**。
> **选型建议：默认用 `flash`**——它在精度与延迟上均不劣于 `v4-pro`，成本低 3.4 倍。
> 也因此，原计划的"按难度路由"没有依据——**而三个候选维度（难度 / 延迟 / 成本）里，
> 只有成本这一条经得起重复测量。**

## 为什么要做这个

我原本的想法很朴素：写个脚本让模型答几道题，算个准确率，放进简历。
做到一半发现，**真正难的不是让模型答题，而是判断它答得对不对。**

第一次跑测（2 道题）就撞上了两类问题：

- 一道题的**答案钥是我写错的**（我凭直觉写了 6，没验算）
- 另一道题模型**明明答对了，却被我的评分器判错**（它说"资源未找到"，我的答案钥写的是"不存在"）

于是这个项目的目标变了：
**不只是评测模型，还要评测我自己的评测体系。**

## 怎么跑

```powershell
# 1. 设 API Key（PowerShell）
$env:DEEPSEEK_API_KEY="你的key"

# 2. 进目录运行
cd <项目目录>
python pipeline.py              # 跑全部 11 题（默认 deepseek-flash）

# 3. 多模型对照（自动跑完两个模型并统计）

python compare_models.py --cases cases_hard.json --rounds 3
```

**结果文件按「模型 + 题库」命名，对照汇总按「题库 + 轮数 + 时间戳」命名，多轮跑测不会互相覆盖。**

## 设计要点

### 1. 题库和程序解耦

题目存在 `cases.json`，**不写死在代码里**。每题结构：

```json
{
  "id": 6,
  "type": "事实问答",
  "prompt": "...",
  "check": "contains_all",
  "answer": [["404"], ["500"], ["不存在", "未找到"], ["服务器"]],
  "note": "判分方式与设计意图",
  "known_issue": "题目歧义"
}
```

### 2. 四类任务，四种评分器

| 任务类型 | 评分器 | 判分方式 |
| --- | --- | --- |
| 算术推理 | `exact` | 精确匹配（剥首尾空白与标点） |
| 代码生成 | `code` | **真的执行代码**，再调用函数验证行为 |
| 事实问答 | `contains_any` / `contains_all` | 关键词命中（支持同义词组） |
| 格式约束 | `json` | 先剥 markdown 标记、再解析 JSON、再比对内容 |

**关键设计：代码题用执行判分，不用眼睛判分。** 模型可以写出很漂亮但跑不通的代码，
也可以写出很丑但完全正确的代码——所以 `exec` 它，然后调用它。

### 3. 同义词组：让答案钥容纳多种措辞

初版答案钥是平铺列表（`["404", "500", "不存在", "服务器"]`），意思是"每个词都必须出现"。
模型答"404：**资源未找到**"，因为没用"不存在"三个字被判错。

改成**分组结构**后：外层每组必须命中，组内命中任一即可。

```json
[["404"], ["500"], ["不存在", "未找到", "找不到"], ["服务器", "服务端", "内部错误"]]
```

> ⚠️ **这个方法有根本局限：它的收敛性已被实测证伪。**
> 换用 `deepseek-flash` 后，模型答"500: **内部错误**"，同义词表没收录 → **同一道题第二次被误判**。
> 扩表是打补丁：**每换一次模型就可能漏一批表述，人工扩表追不上模型的语言变化。**
> 正确方向是语义判分（LLM-as-a-judge），见 [`失败案例.md`](失败案例.md) 案例 5。

### 4. 失败的四种归因

每次失败都打一个原因标签，而不只是记"对/错"：

| 标签 | 含义 |
| --- | --- |
| `能力不足` | 模型确实不会 |
| `格式不合规` | 知道答案，但没按要求的格式输出 |
| `评分器误判` | 内容是对的，是尺子判错了（False Negative） |
| `题目歧义` | 题目本身有问题，多个答案都站得住 |

### 5. 人工标注可以覆盖自动判分

题库里的 `known_issue` 字段由人工复核后填写，主程序优先采用它：

```python
if c.get("known_issue"):
    reason = c["known_issue"]
```

**纯自动判分分不清"模型不会"和"题目有毛病"。** 真实评测系统必须留人工校准的入口。

## 评测结果

**题目**：11 道（4 类任务）　**温度**：`temperature=0`　**单价**：2 元/百万输入 + 8 元/百万输出（高峰价）

一轮换模型的对照很能说明问题：

| 指标 | 旧模型 `deepseek-chat`（已停服） | 现模型 `deepseek-flash` |
| --- | --- | --- |
| 准确率 | 9/11（81.8%）→ 修正后 10/11（90.9%） | **11/11（100%）** |
| 格式约束 | 4/4 | 4/4 |
| 代码生成 | 2/2 | 2/2 |
| **事实问答** | **2/2** | **1/2 → 修正后 2/2** |
| **算术推理** | **1/3（33.3%）** | **3/3** |
| 总成本 | 无法核算（模型名已停服，实际路由未知） | **0.014324 元** |
| 平均每题成本 | — | **0.001302 元** |

> **同一套题，两个模型暴露的短板完全不同**：旧模型算术推理只有 33.3%，新模型算术全对但事实问答
> 因同义词表遗漏被误判。**总分会掩盖这种差异——必须分类看。**
>
> 注：旧模型（`deepseek-chat`）已停服，其总成本无法核算，故本项目不做新旧模型的成本对比。

### 失败归因

| 跑测 | 失败 | 归因 |
| --- | --- | --- |
| `deepseek-chat`（已停服） | 2 道 | 题目歧义 ×1（id 1）、能力不足 ×1（id 11） |
| `deepseek-flash` 首轮 | 1 道 | **评分器误判 ×1（id 6）** |
| `deepseek-flash` 扩表后 | 0 道 | **满分——但这不是好消息** |
| `deepseek-flash` 换题库数据后 | 0 道 | 仍为满分（本次为报告中引用的数据） |

> **失败案例库里六条记录**：**5 条是失败记录，人工复核后全部属评测侧**
> （2 次评分器误判、2 次题目缺陷、1 次题目条件缺失）；
> 第 6 条记的不是失败，是"**零失败导致评测失去信号**"这件事本身。
> 而满分（11/11）反而暴露了更根本的问题：失败归因表变空，评测失去了信号——
> 无法区分"模型变强"和"评分放宽"。详见案例 6。

### 成本在跑测之间波动约 3 倍

同一模型、同一套题，连续三次跑测的总成本：

| 跑测 | 总成本 | 平均每题 |
| --- | --- | --- |
| 第 1 次 | 0.011978 元 | 0.001089 元 |
| 第 2 次 | 0.034986 元 | 0.003181 元 |
| 第 3 次 | 0.014324 元 | 0.001302 元 |

> **出处说明**：第 3 次（**0.014324 元**）可在 `results.json` 里逐条相加复核；
> 第 1、2 次（0.011978 / 0.034986）取自早期跑测记录，**对应的结果文件已不在仓库里**。
> 表中"约 3 倍"的波动结论与后文按题库统计的 1.9~2.6 倍是**两个不同口径**——
> 前者是三次跑测的总成本极值比，后者是单个题库内的 `avg_cost_max ÷ avg_cost_min`。

**关于成因，只能说到观察到的层面**：同一批题里输出长度差异很大
（`results.json` 里 id 6 输出 **276** token、id 8 输出 **101** token）——
**但"成本波动"与"token 波动"之间没有做控制实验，
所以只能说"观察到输出长度在变"，不能说"因为 token 波动所以成本波动"。**
→ **单次跑测的成本不足以作为结论**，成本评估需要多次运行取区间。

### 一个被准确率掩盖的发现

`deepseek-flash` 默认启用思考模式，输出 token 远高于预期：

| 题目 | 要求 | 实际输出 token |
| --- | --- | --- |
| id 6 | 各用四个字以内 | **276** |
| id 11 | 只输出一个数字 | 120 |
| id 8 | 恰好 3 个字 | 101 |

（字段名为 `results.json` 里的 `tokens_out`。）

**"格式合规率 100%"是表面结论。** 答案对了，但**为了守住格式，输出长度被撑得很大**：
要求"四个字以内"的那道题，实际输出 **276 个 token**——
**格式合规不是免费的，"合规率"这个数字本身不体现代价。**

## 失败案例分析

完整记录见 [`失败案例.md`](失败案例.md)，**六条全部来自真实跑测**。

### 案例 1 · 评分器误判（假阴性）

- **题目**：id 6 —— HTTP 404 和 500 分别代表什么
- **模型回答**：`404：资源未找到\n500：服务器错误`（**完全正确**）
- **评分器判定**：❌ 能力不足 → **判错了**
- **原因**：答案钥写的是 `"不存在"`，模型用的是 `"未找到"`，关键词没命中
- **修正**：引入同义词组结构
- **教训**：**答案钥必须来自"实际可能出现的表述"，不能来自出题人脑子里那一句。**

### 案例 2 · 题目歧义 + 答案钥错误

- **题目**：id 1 —— 37 名学生平均分组，每组不超过 6 人，最多几组
- **我的答案钥**：`6`（来源：37÷6≈6，**根本没验算**）
- **真相**：每组人数必须整除 37 → 只能是 1 或 37 → 每组不超过 6 排除 37 → **答案是 37 组**
- **修正**：答案钥 6 → 37，并登记为"指令严密度题"
- **教训**：**答案钥必须验算。** 而且发现答案钥错之后要回头审题面——错往往不只一处。

### 案例 3 · 题目歧义（约束条件缺失）

- **题目**：id 11 —— 16 天生产 1280 件，效率提升 25%，实际要几天
- **模型回答**：第一次 `12.8`（数学精确值）→ 被判错；**第二次 `10`（真算错了）**
- **真相**：`1280÷100 = 12.8`，题目没说"取不取整"，`12.8` 和 `13` 都合理
- **修正**：题面补上"不足一天按一天算"
- **教训**：**出题不是"想一个好问题"，而是"把答案的判定条件也定义清楚"。**
- **额外发现**：同一个模型、同一道题、两次答案不同（12.8 → 10）。
  **`temperature=0` 不等于完全确定**，评测结论需要多次运行才可靠。

### 案例 4 · 纯废题（约束自相矛盾）

- **题目**：id 8 —— 用恰好 3 个字回答中国的首都
- **真相**：首都是"**北京**"，只有 2 个字。题目要求"恰好 3 个字" → **无解**
- **而且答案钥是编的**：出题人写的 `"北京是"` 根本不是首都的名字
- **修正**：保留题目，把考察点从"能否答对"改为"**冲突约束下模型如何取舍**"
  （答"北京"=保内容舍约束；答"北京市"=两者兼顾；答"北京是"=保约束舍内容）
- **教训**：凡"约束 + 答案"互相打架的题，测的不是模型，是出题人的粗心。

### 案例 5 · 同一道题被同义词表遗漏，二次误判

- **题目**：id 6（**与案例 1 同一道题**），模型换成 `deepseek-flash`
- **模型回答**：`404: 未找到 \n500: 内部错误`（**完全正确**）
- **评分器判定**：❌ 能力不足 → **又判错了**
- **原因**：答案钥的服务器组只有 `["服务器","服务端"]`，没收录"内部错误"
- **教训**：**同义词表是打补丁，不具备收敛性。** 案例 1 是"资源未找到"、案例 5 是"内部错误"——
  同一道题、两次误判、原因完全相同，只是换了个说法。**每换一次模型就可能漏一批表述。**
  → 正确方向是**语义判分（LLM-as-a-judge）**，而不是无限扩表。

### 案例 6 · 100% 准确率掩盖了评测效度的缺失

- **现象**：扩表修复后重跑，取得 **11/11 = 100%**，**失败归因表为空**
- **为什么这是问题**：
  1. **无法区分"模型变强"和"评分放宽"**——这次满分紧跟在一次答案钥扩表之后
  2. **失去观察评分器缺陷的机会**——本项目最有价值的产出全部来自失败样本
  3. **题目已无区分度**——11 道题对 `deepseek-flash` 已不能区分能力，继续用它做路由对比得不到有效结论
- **教训**：**准确率不是评测的目的，"能区分"才是。**
  一个让所有被测对象都得满分的测试集，和一个让所有对象都得零分的测试集，**信息量都是零。**

## 多模型成本-效果对照

完整报告见 [`report_model_selection.md`](report_model_selection.md)。

**缘起**：原本打算做"智能路由"——简单任务派小模型、困难任务派大模型。
**但路由要成立，前提是"两个模型存在能力差异"。** 所以在实现之前，先验证这个前提。
结果**前提不成立**，实验目标改为回答"在什么情况下该选哪个模型"。

### 四个测出来的结论

**① 精度：零差异**（最重要）

| 题库 | 题数 | `flash` | `v4-pro` |
| --- | --- | --- | --- |
| 基础（算术/代码/事实/格式） | 11 | **全对（5 轮，每题 5/5）** | 全对（5 轮，每题 5/5） |
| 难度分层 | 6 | **全对（3 轮 × 6 题）** | 全对（3 轮 × 6 题） |

表中数字取自两套题库的可核文件：基础库 5 轮（`compare_base_r5_20260926.json`）、
难题库 3 轮（`compare_results.json`）——两个模型的 `accuracy_stable` 均为 `True`。

难度分层题库含**逻辑量词陷阱**（两道题只差两三个字、答案相反）——**两个模型都答对了。**

> **在这 17 道题覆盖的任务类型上，贵的模型换不到任何可测量的精度提升。**

**② `flash` 的实际成本量级**

| 题库 | 口径 | 单题成本 | 数据源 |
| --- | --- | --- | --- |
| 基础 11 题 | 单次 | 0.001302 元 | `results.json` |
| 基础 11 题 | **5 轮均值** | **0.001418 元** | `compare_base_r5_20260926.json` |
| 难题 6 题 | 单次 | 0.004061 元 | `compare_rebuilt.json` |
| 难题 6 题 | **3 轮均值** | **0.002883 元** | `compare_results_hard.json` |

**两种口径都落在 0.001 ~ 0.004 元 / 题这个量级——1000 道题约 1~4 元，评测这件事本身并不贵。**

> **⚠️ 两个容易读错的地方：**
> **一、**"0.001~0.004"**不是"单题区间"**，是两个题库各自的平均单题成本；
> 而且**同一个题库在不同口径下也不一样**（难题库单次 0.0041、3 轮均值 0.0029）。
> **二、均值会掩盖长尾**——本仓库留存的逐题明细里：
> `flash` 单题最贵 **0.019282 元**（难题库 H2），而 `v4-pro` 有一次到了 **0.095481 元**（基础库 id 1），
> **是同一张卷子其余 10 道题（0.002 ~ 0.009 元）的十几倍**。
> 这与下面那条"留 3 倍余量"是两件事：**余量针对的是均值波动，不覆盖单题长尾。**

**③ 成本不可预测：单题成本在跑测间波动 1.9 ~ 2.6 倍** ⚠️

| 模型 | 基础库 5 轮 | 难题库 3 轮 |
| --- | --- | --- |
| `flash` | **2.64 倍**（0.000963 ~ 0.002541） | **1.87 倍** |
| `v4-pro` | **2.09 倍**（0.003546 ~ 0.007409） | **2.00 倍** |

波动比 = 该题库内 `avg_cost_max ÷ avg_cost_min`，四个数都能在对应结果文件里复算。

**原因**：思考模式下**输出 token 不稳定**（同一道题可能输出几十 token，也可能几百）。

> **直接后果：不能按"上次花了多少"预估这次要花多少。**
> **做预算至少要留 3 倍余量，或者对输出长度加约束。**

**这是本实验最有工程价值的发现**——比"哪个模型便宜"重要得多。

**④ 延迟：两个模型差不多，差异不构成选型依据**

| 题库 | 数据源 | `flash` | `v4-pro` | 差异 |
| --- | --- | --- | --- | --- |
| 基础 11 题 | **5 轮均值** | **1.245s** | **1.261s** | **1.3%** |
| 难题 6 题 | **3 轮均值** | 1.892s | 1.790s | 5.7% |

两个题库上，均值差异都**小于跑测本身的轮间波动**：
基础库 `flash` 的**单轮均值最高到过 2.080s**（比 5 轮均值 1.245s 高 **67%**），
难题库到过 **2.472s**（比 3 轮均值 1.892s 高 **31%**）——
**而两个模型之间的差距只有 1.3% 和 5.7%。所以延迟差异不稳定，不足以作为路由依据。**

> **为什么延迟只报多轮均值：一次长尾调用就足以把结论带偏。**
>
> 同一批请求，两种统计口径给出的答案完全不同：
>
> | 口径 | `flash` | `v4-pro` | 会得出的结论 |
> | --- | --- | --- | --- |
> | 单次跑测 | 1.010s | 2.343s | "`flash` 快 2.32 倍" |
> | **5 轮均值** | **1.245s** | **1.261s** | **"两者持平（差 1.3%）"** |
>
> 差异全在那一次跑测里：**`v4-pro` 有一道题（id 1）花了 16.781 秒**，
> 光这一次调用就占了 1.525 秒的均值（16.781 ÷ 11）——**是那个 2.343s 的 65%**。
> 把它去掉，同一次跑测反而会得出"`v4-pro` 略快"（0.90s vs 1.01s）：
> **方向直接反转，而这同样不可信**——10 个样本里再出现一个长尾，结论就会再翻一次。
>
> **所以延迟和成本一样，只能报多轮均值。**

**顺带一条工程事实**：那次调用同时也是**成本长尾**——它花了 **0.095481 元**，
而那张卷子其余 10 道题都在 **0.002 ~ 0.009 元**之间，**一次调用相当于十几道题**。
**延迟敏感或成本敏感的场景，都要盯尾部，不能只看均值。**

### 选型建议

> **在本题覆盖的任务类型上，默认用 `flash`**——精度与延迟均不劣于 `v4-pro`，成本低 **3.43 倍**（基础库 5 轮均值比）。

| 情况 | 建议 |
| --- | --- |
| 本题库覆盖的任务类型 | 用 `flash`——精度相同，**成本约为 1/3.4**（基础库 5 轮均值比 3.43 倍；难题库 3 轮均值比 3.28 倍） |
| 遇到**未覆盖**且无法实测的新任务类型 | 用 `v4-pro` 兜底——本题库没测到差异，不代表别处也没有 |
| 需要更强推理的**未覆盖**任务 | **先用本仓库脚本实测再决定**，不要凭模型名和价格猜 |
| 任何情况 | **预算留 3 倍余量** |

### 对"路由"的判断

**"按难度路由"不成立**——难度差异不存在，分流无从下手。

**"按延迟路由"同样不成立**——两个模型的延迟差异（1.3% / 5.7%）小于自身的轮间波动，
**路由的前提是"存在稳定的差异"，而这里没有。**

**三个维度试下来，只有成本是稳的**：

| 路由维度 | 是否成立 | 依据 |
| --- | --- | --- |
| 按**难度** | ❌ | 17 道题精度零差异 |
| 按**延迟** | ❌ | 多轮均值差 1.3% / 5.7%，小于轮间波动 |
| 按**成本** | ✅ | 多轮均值口径稳定在 **3.2 ~ 3.4 倍** |

> **换句话说：路由要解决的不是"谁更聪明"、也不是"谁更快"，而是"谁更便宜"。**
> **——三个假设里被数据留下的只有一个。**

### 结论的边界

只测了两个同家族模型、17 道题、短文本单轮无工具场景。
**长上下文、多轮对话、复杂 Agent 任务上，强模型仍可能有优势。**

### 附：成本数字的口径说明

**成本倍数怎么报**：**多轮均值口径下两个题库都在 3.2 ~ 3.4 倍**
（基础库 5 轮 `0.004867 ÷ 0.001418 = 3.43`；难题库 3 轮 `0.009450 ÷ 0.002883 = 3.28`）。
**单次跑测给出的比值则散在 1.85 ~ 12.71 倍之间**——这不是两个模型的关系在变，
而是**单次均值本身就在抖**（见上面 ③：单题成本波动 1.9 ~ 2.6 倍）。
其中基础库那次单跑之所以到 **12.71 倍**，是因为 pro 的总成本 0.127377 元里
**有 0.095481 元来自同一次长尾调用**；把它去掉，同一次跑测的比值就是 **3.50 倍**，
与 5 轮均值的 3.43 倍基本一致。
→ **所以对外只报 3.2 ~ 3.4 倍，单次比值只作为"波动有多大"的例子。**

单题成本波动按题库分别统计：**基础库 flash 2.64 倍 / pro 2.09 倍；难题库 flash 1.87 倍 / pro 2.00 倍**。
**本项目保留的成本结果文件**：`results.json`（11 题单次逐条）、
`compare_base_r5_20260926.json`（基础库 5 轮）、`compare_results_hard.json`（难题库 3 轮）、
`compare_rebuilt.json`（单次逐题明细）。
其中 `compare_rebuilt.json` 的难题库两块，原始文件是
`results_deepseek-flash_cases_hard.json` / `results_deepseek-v4-pro_cases_hard.json`（均已入库）；
基础库两块的原始文件**已被 2026-09-26 的重跑覆盖，仓库内不再留存**——
该次跑测的逐题数据只保存在 `compare_rebuilt.json` 里，可直接在该文件内复核，
所以 `rebuild_compare.py` 在全新克隆上无法重建基础库那一组。

## 已知局限

1. **关键词匹配不具备收敛性。** 同一道题（id 6）在两次跑测中因模型换表述被两次误判，
   每次都靠扩表修复。**扩表永远追不上模型的语言变化**——这是当前设计的最大缺陷。
2. **反向问题：宽松匹配会放进假阳性。** id 8 用 `contains_any`，
   模型若答"不是北京"也会被判通过——所以这道题必须人工复核。
3. **测试集对这两个模型已无区分度。** 11 道基础题 + 6 道难度分层题，
   两个模型都全对——**要区分这代模型，需要长上下文、多轮、带工具的任务**，
   短文本单轮题目已经不够用。
4. **样本量小（11 道）。** 结论只能说明方向，不能当基准。
5. **成本只按高峰价估算。** 空闲时段是半价，若在空闲时段跑测，实际成本约为表中一半。
6. **`exec` 执行模型生成的代码没有沙箱。** 本地评测可以接受，
   生产环境必须放进子进程或容器，限制文件系统与网络访问，并设置超时。
7. **模型名硬编码在代码里。** 旧名 `deepseek-chat` 停服后请求被静默路由到未声明模型，
   成本一度无法归因。**模型名应当集中配置并加有效性校验。**

## 我在这个项目里学到的东西

1. **分数会骗人，归因不会。** 81.8% 也好、100% 也好，数字本身没有信息量。
   拆开才知道问题在哪——**而归因之后发现：失败案例库那 5 条失败记录，全部是评测侧的问题
   （我的尺子、我的题目），没有一条是模型不会。**
2. **答案钥必须验算。** 我犯过两次同样的错（id 1 和 id 11），
   都是"先凭直觉写答案，后跑测"。
3. **评分器也是被测对象。** 一个评测项目如果没有能力质疑自己的尺子，它的结论就不可信。
4. **`temperature=0` 不等于结果确定。** 同一道题两次答案不一样，这是我实测看到的。
5. **满分是危险的信号。** 100% 意味着测试集失去了区分度，
   也意味着我失去了发现评分器缺陷的机会——**评测的价值在于"能区分"，不在于"分数高"。**
6. **别在代码里硬编码模型名。** 官方一停服，请求会被静默路由，
   成本直接无法归因——这是我实测踩到的。
7. **路由的前提是"存在能力差异"。** 差异不存在时，按难度分流就是自我感动——
   **先验证前提，再动手实现。** 我因此砍掉了原本计划的整个项目。
8. **单次结果不能代表稳定水平。** 幻觉率、触发条件、成本倍数、延迟——
   这四件事上单次跑测都给出过误导性的读数，**多次重复才看得出方向**。
9. **数字必须有出处。** 成本倍数只报**多轮均值口径的 3.2 ~ 3.4 倍**——
   单次比值会随跑测在 1.85 ~ 12.71 倍之间乱跳，**写进结论就等于把噪声当信号**。
10. **单点读数会被一次长尾带跑。**
    延迟我报过"基础库 `flash` 快 2.32 倍"，5 轮重跑后发现那只是**一次 16.781 秒的调用**撑起来的；
    真实情况是两个模型持平（1.245s vs 1.261s）。**下结论前要问一句：这个差异会不会只来自一两个样本？**
11. **被数据否定不是失败。** 我砍掉了原本计划的"按难度路由"，
    但换来一条稳健结论（精度无差异）、一条方法论（单点数字不可用）和一套可复用的对照工具。
