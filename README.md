# 大模型评测流水线（LLM Eval Pipeline）

一个从零搭起来的大模型评测脚本：**自定义测试集 → 多类型评分器 → 分类准确率 → 失败案例归因**。

重点不在于"我测了一个模型"，而在于——
**我能说清楚每一次失败到底该怪谁**：是模型不会，还是我的题目/尺子有问题。

---

## 一句话结论

> 对 `deepseek-flash` 跑 11 道题：**准确率 11/11（100%），总成本 0.014324 元，平均每题 0.001302 元。**
> 但**满分不是好消息**——失败归因表随之变空，评测失去了信号。
> 本项目最有价值的产出全部来自失败样本：**失败案例库 6 条记录里，5 条是失败记录，
> 而这 5 条经人工复核后全部属评测侧**（2 次评分器误判、2 次题目缺陷、1 次题目条件缺失）。
> ⚠️ **但我第一版这里写的是"4 条评测侧 + 1 条模型真算错（id 11 第二次答 10）"——
> 那句"模型真算错"我指不回任何文件**：`results.json` 里 id 11 是 `13`／判对，
> 案例库记的是 `12.8` 且复核结论为"题目条件缺失"。
> **所以准确说法就是上面这句：这 5 条全部属评测侧。**
> （另有 1 次模型答错只出现在跑测输出里、没有入库——**没有原始文件，就不当结论讲。**）
>
> ⚠️ **成本在多次跑测间波动约 3 倍**（0.012 ~ 0.035 元）：思考模式下输出 token 不稳定。
> **但这两个数字（0.011978 / 0.034986）的原始文件已被覆盖、仓库里查不到**——
> **能核的是 `results.json` 的 0.014324 元，以及两套题库的 `avg_cost_min/max` 比值——
> 基础库 5 轮 flash 2.64 / pro 2.09，难题库 3 轮 flash 1.87 / pro 2.00。**
> **单次跑测的成本不足以作为结论**，这也是本项目的实测发现之一。

> 一次换模型的对照（旧模型 `deepseek-chat` 已停服）：**算术推理 1/3 → 3/3，事实问答 2/2 → 1/2**，
> 说明同一套题在不同模型上暴露的短板完全不同——**总分会掩盖这种差异，必须分类看。**

> 🔍 **多模型对照的结论（见下）**：
> `flash` 与 `v4-pro` 在 17 道题上**精度零差异**（含两道只差两三个字、答案相反的量词陷阱题）；
> `flash` 处理一道题**平均约 0.001 元**（基础库）/ **约 0.004 元**（难题库），
> 但**跑测之间会跳约 1.9~2.6 倍**（基础库 5 轮 flash 2.64 / pro 2.09；难题库 3 轮 flash 1.87 / pro 2.00，见下），**不能按上次花费预估**；
> **延迟谁快随任务类型变**：基础库 flash 明显快（**2.32 倍**），
> **难题库两者差不多（差 5.7%，小于轮间波动 ±30%）——方向不稳定，不足以作为路由依据。**
> **选型建议：除非有明确的延迟理由，否则用 `flash`。**
> 也因此，我原本计划的"按难度路由"没有依据——**路由该解决的是延迟与成本，不是难度。**

## 为什么要做这个

我原本的想法很朴素：写个脚本让模型答几道题，算个准确率，放进简历。
做到一半发现，**真正难的不是让模型答题，而是判断它答得对不对。**

第一次跑测（2 道题）就撞上了两类问题：

- 一道题的**答案钥是我写错的**（我凭直觉写了 6，没验算）
- 另一道题模型**明明答对了，却被我的评分器判错**（它说"资源未找到"，我的答案钥写的是"不存在"）

于是这个项目的目标变了：
**不只是评测模型，还要评测我自己的评测体系。**

## 怎么跑

```powershell
# 1. 设 API Key（PowerShell）
$env:DEEPSEEK_API_KEY="你的key"

# 2. 进目录运行
cd <项目目录>
python pipeline.py              # 跑全部 11 题（默认 deepseek-flash）
python pipeline.py --limit 2    # 只跑前 2 题（调试用）
python pipeline.py --model deepseek-v4-pro          # 切换被测模型

# 3. 多模型对照（自动跑完两个模型并统计）
```

## 设计要点

### 1. 题库和程序解耦

题目存在 `cases.json`，**不写死在代码里**。每题结构：

```json
{
  "id": 6,
  "type": "事实问答",
  "prompt": "...",
  "check": "contains_all",
  "answer": [["404"], ["500"], ["不存在", "未找到"], ["服务器"]],
  "note": "判分方式与设计意图",
  "known_issue": "题目歧义"
}
```

### 2. 四类任务，四种评分器

| 任务类型 | 评分器 | 判分方式 |
| --- | --- | --- |
| 算术推理 | `exact` | 精确匹配（剥首尾空白与标点） |
| 代码生成 | `code` | **真的执行代码**，再调用函数验证行为 |
| 事实问答 | `contains_any` / `contains_all` | 关键词命中（支持同义词组） |
| 格式约束 | `json` | 先剥 markdown 标记、再解析 JSON、再比对内容 |

**关键设计：代码题用执行判分，不用眼睛判分。** 模型可以写出很漂亮但跑不通的代码，
也可以写出很丑但完全正确的代码——所以 `exec` 它，然后调用它。

### 3. 同义词组：让答案钥容纳多种措辞

初版答案钥是平铺列表（`["404", "500", "不存在", "服务器"]`），意思是"每个词都必须出现"。
模型答"404：**资源未找到**"，因为没用"不存在"三个字被判错。

改成**分组结构**后：外层每组必须命中，组内命中任一即可。

```json
[["404"], ["500"], ["不存在", "未找到", "找不到"], ["服务器", "服务端", "内部错误"]]
```

> ⚠️ **这个方法有根本局限，已被实测证伪其收敛性。**
> 换用 `deepseek-flash` 后，模型答"500: **内部错误**"，同义词表没收录 → **同一道题第二次被误判**。
> 说明扩表是打补丁：**每换一次模型就可能漏一批表述，人工扩表追不上模型的语言变化。**
> 正确方向是语义判分（LLM-as-a-judge），见 [`失败案例.md`](失败案例.md) 案例 5。

### 4. 失败的四种归因

每次失败都打一个原因标签，而不只是记"对/错"：

| 标签 | 含义 |
| --- | --- |
| `能力不足` | 模型确实不会 |
| `格式不合规` | 知道答案，但没按要求的格式输出 |
| `评分器误判` | 内容是对的，是尺子判错了（False Negative） |
| `题目歧义` | 题目本身有问题，多个答案都站得住 |

### 5. 人工标注可以覆盖自动判分

题库里的 `known_issue` 字段由人工复核后填写，主程序优先采用它：

```python
if c.get("known_issue"):
    reason = c["known_issue"]
```

**纯自动判分分不清"模型不会"和"题目有毛病"。** 真实评测系统必须留人工校准的入口。

## 评测结果

**题目**：11 道（4 类任务）　**温度**：`temperature=0`　**单价**：2 元/百万输入 + 8 元/百万输出（高峰价）

一轮换模型的对照很能说明问题：

| 指标 | 旧模型 `deepseek-chat`（已停服） | 现模型 `deepseek-flash` |
| --- | --- | --- |
| 准确率 | 9/11（81.8%）→ 修正后 10/11（90.9%） | **11/11（100%）** |
| 格式约束 | 4/4 | 4/4 |
| 代码生成 | 2/2 | 2/2 |
| **事实问答** | **2/2** | **1/2 → 修正后 2/2** |
| **算术推理** | **1/3（33.3%）** | **3/3** |
| 总成本 | 无法核算（模型名已停服，实际路由未知） | **0.014324 元**（多次跑测区间 0.012 ~ 0.035） |
| 平均每题成本 | — | **0.001302 元** |

> **同一套题，两个模型暴露的短板完全不同**：旧模型算术推理只有 33.3%，新模型算术全对但事实问答
> 因同义词表遗漏被误判。**总分会掩盖这种差异——必须分类看。**

### 失败归因

| 跑测 | 失败 | 归因 |
| --- | --- | --- |
| `deepseek-chat`（已停服） | 2 道 | 题目歧义 ×1（id 1）、能力不足 ×1（id 11） |
| `deepseek-flash` 首轮 | 1 道 | **评分器误判 ×1（id 6）** |
| `deepseek-flash` 扩表后 | 0 道 | **满分——但这不是好消息** |
| `deepseek-flash` 换题库数据后 | 0 道 | 仍为满分（本次为报告中引用的数据） |

> **失败案例库里六条记录**：**5 条是失败记录，人工复核后全部属评测侧**
> （2 次评分器误判、2 次题目缺陷、1 次题目条件缺失）；
> 第 6 条记的不是失败，是"**零失败导致评测失去信号**"这件事本身。
> （⚠️ 我先前写过"其中 1 条是模型真算错（id 11 第二次答 10）"——**那个说法指不回文件，已撤回。**）
> 而满分（11/11）反而暴露了更根本的问题：失败归因表变空，评测失去了信号——
> 无法区分"模型变强"和"评分放宽"。详见案例 6。

### 成本在跑测之间波动约 3 倍

同一模型、同一套题，连续三次跑测的总成本：

| 跑测 | 总成本 | 平均每题 |
| --- | --- | --- |
| 第 1 次 | 0.011978 元 | 0.001089 元 |
| 第 2 次 | 0.034986 元 | 0.003181 元 |
| 第 3 次 | 0.014324 元 | 0.001302 元 |

**关于成因，我只能说到观察到的层面**：同一批题里输出长度差异很大
（`results.json` 里 id 6 输出 **276** token、id 8 输出 **101** token）——
**但"成本波动 3 倍"与"token 波动"之间我没有做控制实验，
所以只能说"我观察到输出长度在变"，不能说"因为 token 波动所以成本波动"。**
→ **单次跑测的成本不足以作为结论**，成本评估需要多次运行取区间。

> **⚠️ 这里我改了两次，两次都值得记下来**
> 1. 原写"同一道题 **78 ~ 235** token"——**那 78 和 235 是两个错数字，而且分属两道题**；
> 2. 我第一版更正写成"同一道题 **101 ~ 276** token"——**还是错的，101 和 276 同样是两道题**。
> **两次都是"拿两个数凑成一个区间"就往上写，没有先确认它们是不是同一对象的测量。**
> 现在的写法只陈述能核的事实，成因部分明确标为"未做控制实验"。

### 一个被准确率掩盖的发现

`deepseek-flash` 默认启用思考模式，输出 token 远高于预期：

| 题目 | 要求 | 实际输出 token |
| --- | --- | --- |
| id 6 | 各用四个字以内 | **276** |
| id 11 | 只输出一个数字 | 120 |
| id 8 | 恰好 3 个字 | 101 |

**"格式合规率 100%"是表面结论。** 答案对了，但**为了守住格式，输出长度被撑得很大**：
要求"四个字以内"的那道题，实际输出 **276 个 token**（`results.json` 可核）——
**格式合规不是免费的，"合规率"这个数字本身不体现代价。**

> **⚠️ 更正**：这三个数原来写的是 **235 / 113 / 78**，**全部与 `results.json` 不符**
> （该文件里分别是 **276 / 120 / 101**，字段名是 `tokens_out`）。
> **而那句"（`results.json` 可核）"是我自己写上去的——写了却没核，比不写更糟。**

> **⚠️ 这里我删掉了一句原先写过的话**：我原来写的是"**付出的成本是旧模型的数倍**"。
> **那句话没有数据支撑**——旧模型（`deepseek-chat`）已停服，它那次跑测**总成本无法核算**
> （见上文"评测结果"表：总成本一栏写的就是"无法核算"）。**没有两个可比数字，就不该说"数倍"。**

## 失败案例分析

完整记录见 [`失败案例.md`](失败案例.md)，**六条全部来自真实跑测**。

### 案例 1 · 评分器误判（假阴性）

- **题目**：id 6 —— HTTP 404 和 500 分别代表什么
- **模型回答**：`404：资源未找到\n500：服务器错误`（**完全正确**）
- **评分器判定**：❌ 能力不足 → **判错了**
- **原因**：答案钥写的是 `"不存在"`，模型用的是 `"未找到"`，关键词没命中
- **修正**：引入同义词组结构
- **教训**：**答案钥必须来自"实际可能出现的表述"，不能来自出题人脑子里那一句。**

### 案例 2 · 题目歧义 + 答案钥错误

- **题目**：id 1 —— 37 名学生平均分组，每组不超过 6 人，最多几组
- **我的答案钥**：`6`（来源：37÷6≈6，**根本没验算**）
- **真相**：每组人数必须整除 37 → 只能是 1 或 37 → 每组不超过 6 排除 37 → **答案是 37 组**
- **修正**：答案钥 6 → 37，并登记为"指令严密度题"
- **教训**：**答案钥必须验算。** 而且发现答案钥错之后要回头审题面——错往往不只一处。

### 案例 3 · 题目歧义（约束条件缺失）

- **题目**：id 11 —— 16 天生产 1280 件，效率提升 25%，实际要几天
- **模型回答**：第一次 `12.8`（数学精确值）→ 被判错；**第二次 `10`（真算错了）**
- **真相**：`1280÷100 = 12.8`，题目没说"取不取整"，`12.8` 和 `13` 都合理
- **修正**：题面补上"不足一天按一天算"
- **教训**：**出题不是"想一个好问题"，而是"把答案的判定条件也定义清楚"。**
- **额外发现**：同一个模型、同一道题、两次答案不同（12.8 → 10）。
  **`temperature=0` 不等于完全确定**，评测结论需要多次运行才可靠。

### 案例 4 · 纯废题（约束自相矛盾）

- **题目**：id 8 —— 用恰好 3 个字回答中国的首都
- **真相**：首都是"**北京**"，只有 2 个字。题目要求"恰好 3 个字" → **无解**
- **而且答案钥是编的**：出题人写的 `"北京是"` 根本不是首都的名字
- **修正**：保留题目，把考察点从"能否答对"改为"**冲突约束下模型如何取舍**"
  （答"北京"=保内容舍约束；答"北京市"=两者兼顾；答"北京是"=保约束舍内容）
- **教训**：凡"约束 + 答案"互相打架的题，测的不是模型，是出题人的粗心。

### 案例 5 · 同一道题被同义词表遗漏，二次误判

- **题目**：id 6（**与案例 1 同一道题**），模型换成 `deepseek-flash`
- **模型回答**：`404: 未找到 \n500: 内部错误`（**完全正确**）
- **评分器判定**：❌ 能力不足 → **又判错了**
- **原因**：答案钥的服务器组只有 `["服务器","服务端"]`，没收录"内部错误"
- **教训**：**同义词表是打补丁，不具备收敛性。** 案例 1 是"资源未找到"、案例 5 是"内部错误"——
  同一道题、两次误判、原因完全相同，只是换了个说法。**每换一次模型就可能漏一批表述。**
  → 正确方向是**语义判分（LLM-as-a-judge）**，而不是无限扩表。

### 案例 6 · 100% 准确率掩盖了评测效度的缺失

- **现象**：扩表修复后重跑，取得 **11/11 = 100%**，**失败归因表为空**
- **为什么这是问题**：
  1. **无法区分"模型变强"和"评分放宽"**——这次满分紧跟在一次答案钥扩表之后
  2. **失去观察评分器缺陷的机会**——本项目最有价值的产出全部来自失败样本
  3. **题目已无区分度**——11 道题对 `deepseek-flash` 已不能区分能力，继续用它做路由对比得不到有效结论
- **教训**：**准确率不是评测的目的，"能区分"才是。**
  一个让所有被测对象都得满分的测试集，和一个让所有对象都得零分的测试集，**信息量都是零。**

## 多模型成本-效果对照

完整报告见 [`report_model_selection.md`](report_model_selection.md)。

**缘起**：原本打算做"智能路由"——简单任务派小模型、困难任务派大模型。
**但路由要成立，前提是"两个模型存在能力差异"。** 所以在实现之前，先验证这个前提。
结果**前提不成立**，实验目标改为回答"在什么情况下该选哪个模型"。

### 四个测出来的结论

**① 精度：零差异**（最重要）

| 题库 | 题数 | `flash` | `v4-pro` |
| --- | --- | --- | --- |
| 基础（算术/代码/事实/格式） | 11 | **全对**（基础库单次 11/11，两个模型都是） | 全对 |
| 难度分层 | 6 | **全对（3 轮 × 6 题全对）** | 全对 |

**这是本实验最有工程价值的发现**——比"哪个模型便宜"重要得多。

**④ 延迟：谁快取决于任务类型**

| 题库 | 谁更快 | 倍数（慢的 ÷ 快的） |
| --- | --- | --- |
| 基础 11 题（单次重建） | **flash** 快 | **2.32 倍**（1.010s vs 2.343s） |
| 难题 6 题（3 轮均值） | pro 略快 | **1.06 倍**（1.892s vs 1.790s） |

>
> **① 倍数我算错过一次**：这里原写"pro 快 **1.24 倍**"——**而同一行给出的两个数
> `1.892 ÷ 1.790` = 1.06**。1.24 是我凭印象填的，没有任何出处。已改成 1.06。
>
> **② "方向反转"这个说法太满**：难题库上两者只差 **5.7%**，
> 而**同一份数据里，flash 的单轮均值最高到过 2.4717（比三轮均值高 30.6%）**——
> **轮间摆动是模型间差距的 5 倍以上。**
> **所以准确说法是：难题库上两个模型"差不多"，方向不稳定，不足以作为路由依据。**
>
> （我原先还写过"基础库 flash 快 **21%**、难题库 **pro 快 63%**"。

**方向会反转。** 所以"贵的模型更快、值得为速度付费"这个假设**不成立**，
必须先在自己的任务类型上实测。（单题最慢曾出现 **16.78 秒**——延迟敏感场景要看尾部。）

### 选型建议

> **除非有明确的延迟理由，否则用 `flash`。**

| 情况 | 建议 |
| --- | --- |
| 本题库覆盖的任务类型 | 用 `flash`——精度相同，成本低一个量级 |
| 需要更强推理的**未覆盖**任务 | **先用本仓库脚本实测再决定**，不要凭模型名和价格猜 |
| 延迟敏感 | 先在自己的任务类型上实测，**延迟优势可能反转** |
| 任何情况 | **预算留 3 倍余量** |

### 对"路由"的判断

**"按难度路由"不成立**——难度差异不存在，分流无从下手。
**但路由仍然有价值，只是要换维度**：按**延迟**、按**成本**路由是成立的。

> **路由要解决的不是"谁更聪明"，而是"谁更便宜 / 更快"。**

### 结论的边界

只测了两个同家族模型、17 道题、短文本单轮无工具场景。
**长上下文、多轮对话、复杂 Agent 任务上，强模型仍可能有优势。**

## 已知局限（这个项目还不够好的地方）

1. **关键词匹配不具备收敛性。** 同一道题（id 6）在两次跑测中因模型换表述被两次误判，
   每次都靠扩表修复。**扩表永远追不上模型的语言变化**——这是当前设计的最大缺陷。
2. **反向问题：宽松匹配会放进假阳性。** id 8 用 `contains_any`，
   模型若答"不是北京"也会被判通过——所以这道题必须人工复核。
3. **测试集对这两个模型已无区分度。** 11 道基础题 + 6 道难度分层题，
   两个模型都全对——**要区分这代模型，需要长上下文、多轮、带工具的任务**，
   短文本单轮题目已经不够用。
4. **样本量小（11 道）。** 结论只能说明方向，不能当基准。
5. **成本只按高峰价估算。** 空闲时段是半价，若在空闲时段跑测，实际成本约为表中一半。
6. **`exec` 执行模型生成的代码没有沙箱。** 本地评测可以接受，
   生产环境必须放进子进程或容器，限制文件系统与网络访问，并设置超时。
7. **模型名硬编码在代码里。** 旧名 `deepseek-chat` 停服后请求被静默路由到未声明模型，
   成本一度无法归因。**模型名应当集中配置并加有效性校验。**

## 我在这个项目里学到的东西

1. **分数会骗人，归因不会。** 81.8% 也好、100% 也好，数字本身没有信息量。
   拆开才知道问题在哪——**而归因之后发现：失败案例库那 5 条失败记录，全部是评测侧的问题
   （我的尺子、我的题目），没有一条是模型不会。**
   > ⚠️ **这一条我改了三版，第三版才对。** 第一版写"六条记录没有一次是模型的错"（与自己的归因表打架）；
   > 第二版改成"4 条评测侧 + 1 条模型真算错"（**那个"1 条"我指不回文件**）；
   > **现在这版是唯一能被案例库和 `cases.json` 同时支持的**。
2. **答案钥必须验算。** 我犯过两次同样的错（id 1 和 id 11），
   都是"先凭直觉写答案，后跑测"。
3. **评分器也是被测对象。** 一个评测项目如果没有能力质疑自己的尺子，它的结论就不可信。
4. **`temperature=0` 不等于结果确定。** 同一道题两次答案不一样，这是我实测看到的。
5. **满分是危险的信号。** 100% 意味着测试集失去了区分度，
   也意味着我失去了发现评分器缺陷的机会——**评测的价值在于"能区分"，不在于"分数高"。**
6. **别在代码里硬编码模型名。** 官方一停服，请求会被静默路由，
   成本直接无法归因——这是我实测踩到的。
7. **路由的前提是"存在能力差异"。** 差异不存在时，按难度分流就是自我感动——
   **先验证前提，再动手实现。** 我因此砍掉了原本计划的整个项目。
8. **单次结果不能代表稳定水平。** 这条我在同一个项目里踩了三次（幻觉率、触发条件、成本倍数），
   每次都是"跑一次就下结论"。
9. **数字必须有出处。** 我口头报过一个"贵 7.7 倍"，**后来发现连我用来替换它的"4.1 倍"也查不到出处**
   （分子 `0.058986` 不在任何数据文件里）——**凭印象报的数字，迟早会在最不该出错的地方出错。**
   **能站住的只有区间：1.85 ~ 12.71 倍。**
10. **单点结论会随条件反转。** 我先写下"flash 延迟更低"，后来按题库分开看，
    **难题库上两者只差 5.7%（小于轮间波动 ±30%）**——
    **下结论前要问一句"换个条件还成立吗"。**
    （⚠️ 我原先这里写的是"难题库 pro 快 **63%**"——**那个 63% 是读反了**：
    它其实是"flash 比 pro 慢 63%"，而且用的是单次数据。）
11. **被数据否定不是失败。** 我砍掉了原本计划的"按难度路由"，
    但换来一条稳健结论（精度无差异）、一条方法论（单点数字不可用）和一套可复用的对照工具。
